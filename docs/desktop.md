# Manager 데스크톱 사용법

이 문서는 macOS 1차 출시 범위의 로컬 설치·시작·정지·재시작·상태와 작업 기록을 다룬다. 백업 생성·인증·새 설치 복원과 관리 공간 선택, 서명된 업데이트 적용·원래 전시 전체 복원 화면이 같은 lifecycle 코어에 연결돼 있다. 화면 연결과 실제 네이티브 GUI·전체 업데이트·롤백 검증은 구분하며, 후자는 아직 완료되지 않았다. 기존 원격·클라우드 배포 준비 구현은 보존하지만 1차 필수 범위가 아니다. Manager 자체와 실행하는 Platform은 서로 다른 라이선스를 유지한다.

## 화면 이동과 화면 모드

기본 **간편 화면**에서는 상단의 **전시 · 백업·복원 · 업데이트 · 작업 기록 · 배포 준비**로 현재 목적에 필요한 기존 패널을 선택한다. 처음에는 Studio 준비와 현재 전시 상태를 보여준다. **고급 설정**은 같은 패널의 수동 설치·관리 공간·세부 서비스·진단과 기존 서버 배포 도구를 함께 펼친다. 다시 **간편 화면**으로 돌아가도 입력·선택·작업 상태는 초기화하지 않는다. 목적 링크와 브라우저 뒤로/앞으로 이동은 같은 전시 데이터와 실행 코어를 사용한다.

진행 중·실패·필수 복구나 완료 여부 미확인 상태는 다른 목적을 보고 있어도 해당 패널에 표시한다. 작업 완료 안내도 현재 목적 화면 바깥에서 읽을 수 있다. 단순한 화면 전환으로 작업을 취소하거나 데이터를 변경하지 않는다. 실제로 표시된 목적 영역으로 키보드 초점을 옮기며 숨겨진 패널의 입력은 탭 순서에서 제외한다.

**배포 준비**나 **고급 설정**을 처음 열기 전에는 Cloudflare/Render 연결·기존 배포 기록을 조회하지 않는다. 로컬 Studio 준비 때문에 클라우드 키체인을 읽지 않는다. 최초 진입 후에는 동일 배포 컴포넌트를 유지해 입력을 보존하고 반복 진입마다 초기 조회를 반복하지 않는다. 배포 화면 진입 시 기존 작업을 읽지만 화면을 열었다는 이유로 원격 배포를 취소하거나 다시 실행하지 않는다.

긴 고급 화면에서도 목차는 유지된다. **화면 모드**의 기본값은 시스템 설정이며 **라이트 / 다크**를 직접 선택하면 다음 실행에도 유지한다. 이 선택은 서버·관리 공간·인증 정보에 영향을 주지 않는다.

## Studio를 준비하고 열기

**전시 만들기·이어서 편집하기**에서 **Studio 준비하고 열기**를 누르면 현재 선택한 설치를 확인하고, 필요한 전시 설치·시작을 기존 실행 코어로 차례로 처리합니다. 각 작업의 완료와 서버 응답 준비를 확인한 뒤 기본 브라우저에 Studio 열기를 요청합니다. 이미 준비된 설치는 다시 설치하거나 시작하지 않습니다. Studio에서는 기존 지원 작품을 가져와 편집할 수 있으며 Capture·Mac Processing이나 클라우드 계정은 필수가 아닙니다.

실패·진행 중인 작업이나 관리 공간 변경이 발견되면 다음 단계로 넘어가지 않습니다. 작업 기록과 안내를 확인한 뒤 다시 시도하세요. 완료된 설치를 재사용하며, 앱 재실행만으로 이 준비 흐름이나 브라우저를 자동 실행하지 않습니다. **세부 안내 보기**는 설명만 펼치고 기존 입력·작업 상태는 유지합니다. 브라우저 실행 요청은 Studio의 작품 가져오기·편집·저장 성공을 뜻하지 않습니다.

이 연결은 실행 도구 설치나 runtime bundle 자동 다운로드를 구현한 것이 아닙니다. 현재 개발판에는 아래의 실행 도구·검증된 패키지 준비가 여전히 필요합니다. 전체 간편·고급 화면 정리와 개발 도구 없는 배포판의 실제 첫 설치 검증도 남아 있습니다.

2026-10-17 검증: 준비 코어 단위6개, 합성 IPC를 사용하는 Chromium 실제 화면 조작13개와 타입·lint·프런트엔드 빌드가 통과했습니다. 이는 실제 네이티브 설치·엔진 실행·Studio 서버 편집·서명·공증 검증과 구분합니다. 정확한 소스와 제한은 [검증 기록](studio-setup-verification-2026-10-17.json)에 있습니다.

## 처음 실행하기

1. Docker 또는 Podman과 해당 Compose 도구를 설치하고 실행한다. 실행 도구 설치 과정의 OS 관리자 승인과 사용자 계정 설정은 컴퓨터 소유자가 수행한다. 설치 여부만으로 사용 가능하다고 표시하지 않으며 실제 엔진 연결을 검사한다.
2. 운영자가 검증한 ExhibitOS runtime bundle을 아래의 지정 경로에 준비한다. 현재 개발 앱은 runtime image를 자동 다운로드하는 설치 프로그램이 아니다. bundle이 없는 상태에서는 설치가 실패하고 복구 안내를 표시한다.
3. `ExhibitOS Manager.app`을 연다. **실행 도구 다시 확인**을 눌러 사용 가능 상태를 확인한다. **저장 공간**에서 디스크 여유 공간과 필요한 여유 공간을 확인한다. 전시 사용량을 측정할 수 없으면 그 사실을 표시한다. 안내 용량은 강제 quota가 아니다.
4. **Studio 준비하고 열기**를 누른다. 필요한 설치·시작을 기존 검증으로 연결하며 각 단계가 완료되지 않으면 다음으로 넘어가지 않는다. **작업 기록**에서 완료 또는 실패 안내를 확인한다. 고급 설정에서는 기존 **전시 설치**와 **시작**을 따로 실행할 수 있다. 설치 완료는 서버 준비 완료를 뜻하지 않는다.
5. 서버 준비를 확인한 뒤 기본 브라우저에 Studio 열기를 요청한다. 관객 화면은 상태 카드의 **전시 열기**로 확인한다. 지정된 로컬 주소만 열며 외부 주소나 임의 명령은 입력할 수 없다.
6. 간편 화면의 **전시 정지**(고급의 **정지**)는 container 실행을 중단하며 저장 volume을 삭제하지 않는다. **다시 시작**(고급의 **재시작**)은 정지 후 다시 시작한다. 실패하면 안내를 해결한 다음 **실패한 작업 다시 시도**를 사용한다. 앱을 다시 열어도 작업 기록이 남는다. 중단된 작업은 성공으로 표시하지 않는다.

서명·공증이 없는 개발 앱은 macOS가 실행 확인을 요구할 수 있다. 배포 서명·공증과 Windows 설치 검증은 별도 검증 항목이며 개발 빌드 성공으로 대신하지 않는다. 시스템 보안 기능을 일괄 해제하지 않는다.

## 운영자가 준비하는 경로

기본 root는 Tauri가 반환하는 OS app-data 경로 아래의 `local-runtime`이다. macOS identifier는 `org.exhibitos.manager`이다. 개발·검증은 실행 프로세스의 `EXHIBITOS_MANAGER_ROOT`에 절대 경로를 지정해 사용자 데이터와 격리한다. 일반 macOS 앱은 [관리 공간 선택](installation-selection.md)으로 앱이 관리하는 새 공간 또는 등록된 공간을 선택한다. 임의 폴더·Compose 파일은 선택하지 않는다.

root 안의 `bundle/manifest.json`, `bundle/compose.yaml`과 manifest에 지정된 image archive는 신뢰한 배포 채널에서 받아 준비한다. 자체 파일 해시는 잘못된 파일을 감지하지만 신뢰하지 않은 배포자를 신뢰하게 만들지는 않는다. 운영자는 bundle 출처와 게시된 해시를 별도로 검증한다. manifest의 version/protocol, image digest, archive 크기·해시, services, ports, readiness URL과 최소 여유 공간은 lifecycle core의 검증을 통과해야 한다. Compose 프로젝트와 저장 volume은 해당 root의 관리 대상으로 격리한다.

Finder에서 실행할 때도 backend는 표준 Docker/Podman 설치 경로를 검사한다. 엔진 daemon이 정지했거나 Compose가 없으면 안내에 따라 실행 도구를 준비하고 다시 확인한다. Manager는 관리자 암호나 registry token을 입력받지 않고 raw container 로그를 화면에 노출하지 않는다.

실행 도구가 응답하지 않으면 `ENGINE_UNAVAILABLE`, 접근이 거부되면
`ENGINE_PERMISSION`, 제한 시간 안에 응답하지 않으면 `ENGINE_TIMEOUT`으로
안내한다. Compose provider가 실행되지 않으면 `COMPOSE_UNAVAILABLE`이다.
버전 문자열을 정상적으로 확인한 뒤 지원 범위를 벗어났을 때만
`VERSION_MISMATCH`를 표시하며, raw 오류 출력이나 credential을 반환하지 않는다.

manifest에 `preferredEngine`이 명시되면 그 패키지를 만든 실행 도구를 요구한다.
해당 도구가 꺼져 있어도 다른 도구로 자동 전환하지 않는다. 이 필드가 없는 기존
bundle은 사용 가능한 도구를 선택할 수 있다. 설치의 image 검증이 모두 통과한
뒤에만 engine 선택을 기록하며, 실패한 초기 설치의 임시 선택은 retry를 고정하지
않는다. 설치 완료된 root의 실행 도구는 유지하며, 다른 producer를 요구하는
bundle을 덮어 설치하는 동작은 거부한다.


## 개발 빌드와 검사

Node 24.21.0/npm 11.19.0과 `rust-toolchain.toml`의 Rust를 사용한다. macOS의 네이티브 compiler/SDK가 필요하다. Windows는 해당 OS의 Tauri 빌드 요구 사항과 실제 설치·실행 검증이 추가로 필요하다.

```sh
npm ci
npm run check
npm run test:browser
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
npm run desktop:build
```

macOS 개발 결과는 `target/release/bundle/macos/ExhibitOS Manager.app`이다. `npm run desktop:dev`는 로컬 Vite 서버와 네이티브 앱을 함께 시작한다. `npm run dev`만 실행해서 여는 브라우저 화면은 디자인·접근성 확인용이며 실제 lifecycle 권한이 없어 제어 버튼이 비활성화된다. browser test는 실제 네이티브 작업 성공을 증명하지 않는다.

프로젝트 안의 격리된 Rust 도구를 사용하는 경우 다음 환경을 설정한 같은 terminal에서 검사한다. 경로는 자신의 checkout에 맞춘다. 토큰·암호를 명령 인수에 넣지 않는다.

```sh
export RUSTUP_HOME="/absolute/ExhibitOS/.local/toolchains/rustup"
export CARGO_HOME="/absolute/ExhibitOS/.local/toolchains/cargo"
export PATH="$CARGO_HOME/bin:$PATH"
export EXHIBITOS_MANAGER_ROOT="/absolute/isolated-manager-runtime"
npm run desktop:build
```

## 데스크톱 권한 경계

앱은 번들된 로컬 webview 한 개만 사용한다. 원격 문서 탐색을 차단하고 CSP와 main-window 전용 capability를 적용한다. Rust IPC는 앱에 등록된 고정 Manager 명령만 허용한다. 상태·설치·실행·관리 공간·백업·복원·업데이트·롤백 요청은 해당 명령의 닫힌 입력 형식과 lifecycle 코어의 권한·현재 상태 검사를 통과해야 한다. 파일 시스템·shell plugin과 임의 URL 열기는 노출하지 않는다. 실행 작업은 blocking worker에서 처리해 화면의 상태 조회를 유지한다.

권한 설정의 근거는 Tauri의 [보안 경계](https://v2.tauri.app/security/), [capabilities](https://v2.tauri.app/security/capabilities/)와 [permissions](https://v2.tauri.app/security/permissions/) 문서다. frontend 입력 검사는 사용성을 위한 추가 검사이며 엔진 실행 권한은 Rust lifecycle core에서 검증한다.

## 검증 범위 기록

실제 명령 결과와 기기·엔진 정보는 해당 commit의 검증 기록에 남긴다. 웹 preview, Rust 단위 검사, macOS 앱 빌드, 네이티브 GUI, 실제 engine 설치·시작·정지, Windows, 서명·공증을 구분한다. 하나의 성공을 다른 검증의 성공으로 기록하지 않는다. 백업·복원·업데이트 화면의 완료 표시는 실제 응답과 저장된 작업 상태에 따른다. helper 실행 요청·앱 닫기 대기·진행 중·실패·중단을 완료로 표시하지 않는다. 브라우저의 합성 응답에 대한 표시 검사는 실제 복구나 업데이트 성공 증거가 아니다.

## Podman 개발 검사

실제 검사 후보는 rootless Podman6.1.3와 독립 Compose5.5.1 제공자이다.
같은 실행 환경에서 `PODMAN_COMPOSE_PROVIDER`를 해당 독립 CLI 경로로 설정한다.
필요한 경우 `CONTAINER_CONNECTION`으로 검증용 named connection을 지정한다.
Docker Desktop 서버와 privileged socket helper를 설치할 필요는 없다.
Compose1.x 제공자는 이 adapter의 JSON 계약에 맞지 않아 준비 완료로 표시하지 않는다.
이미지 archive의 engine별 ID는 서로 다를 수 있으므로 해당 producer의 bundle을
사용한다. sha256 접두어 차이만 정규화하며 다른 digest는 거부한다.
기존 VM·연결·사용자 데이터는 변경하거나 자동 삭제하지 않는다.

## 상태와 실패 안내 읽기

화면 위 **다음 할 일**은 확인된 설치·실행 상태에 따라 다음 조작을 안내합니다. 실행 중에는 중복 작업을 막고 **작업 진행과 복구** 영역에 저장된 진행률을 표시합니다. 진행률은 backend 작업 기록이며 남은 시간을 예측하지 않습니다. 실패·중단 후에는 복구 안내를 해결한 다음 **실패한 작업 다시 시도**를 누릅니다. 상태 확인을 다시 하는 것은 설치나 시작 작업을 재실행하는 동작이 아닙니다.

서비스의 **실행 중**과 **응답 정상**은 서로 다른 상태입니다. 서비스가 실행 중이어도 서버 준비가 완료되기 전에는 **전시 열기**가 활성화되지 않습니다. 알 수 없는 서비스 상태는 확인 필요로 표시하며 성공으로 추측하지 않습니다. **안전한 진단 기록**을 펼쳐 부가 정보를 확인할 수 있습니다.

실패·중단 후 남은 보조 실행은 [helper 확인과 정지](helper-reconciliation.md)에서 명시적으로 확인할 수 있다. 원래 작업을 성공 처리하거나 후보 데이터를 삭제하지 않는다. 실행 중인 백업·복원의 취소 요청과 실제 정지 확인은 [유지보수 작업 취소](maintenance-cancellation.md)의 별도 경로를 사용하며, 취소 요청 자체를 정지 완료로 표시하지 않는다.

## Windows 실행 도구 콘솔

상태를 3초마다 확인하는 동안 Docker/Podman과 비대화형 보조 프로세스는 Windows `CREATE_NO_WINDOW`로 실행한다. 출력·오류 수집, 종료 코드와 제한 시간은 유지한다. 이미지 스트리밍 내보내기도 같은 실행 설정을 쓴다. Docker Desktop 자체를 종료하거나 데이터를 지우는 설정은 아니다.

Windows에서는 `cargo test -p exhibitos-lifecycle process_window --locked`가 실제 자식 프로세스의 콘솔 핸들이 없는지와 stdout/stderr·실패 종료 코드 보존을 확인한다. 최종 확인은 새로 빌드한 앱을 열고 30초 이상 Docker 감지와 상태 갱신을 관찰하는 것이다. Mac 검사 또는 Windows 대상 컴파일만으로 실제 Windows 창 검사를 통과했다고 기록하지 않는다.

## 처음 사용할 로컬 계정

새 설치에서 **Studio 준비하고 열기** 또는 **전시 설치**를 누르면 작품 관리·서버 저장에 사용할 계정과 비밀번호를 설정합니다. 클라우드 가입은 필요 없습니다. 비밀번호 확인이 일치해야 계속할 수 있고, **취소**하면 계정 설정과 설치를 시작하지 않습니다. 기존 설치의 계정·비밀번호는 이 화면에서 변경하지 않습니다.

입력은 선택한 설치의 비공개 설정으로만 전달합니다. 저장된 비밀번호는 Manager 상태 응답·로그·Studio 주소에 반환하지 않습니다. 준비된 Studio에서 **CMS에서 로그인**을 누르면 같은 설치의 기관과 계정이 채워집니다. 설정한 비밀번호로 기존 로그인 절차를 완료하세요. 이 정보는 로그인 힌트이며 접근 권한을 부여하지 않습니다. 직접 실행한 Platform의 일반 로그인도 유지됩니다.

새 비밀번호는 입력 문자가 바뀌지 않는 형식으로 저장하고 기존 원문 형식도 읽습니다. 백업·복원은 원래 설정 바이트를 보존하며 비밀번호를 새로 만들지 않습니다. 설치가 실패한 뒤 이미 계정 설정이 보관됐다면 처음 입력한 비밀번호를 사용합니다. 기존 설정이 없거나 손상된 설치를 새 계정으로 초기화하지 않습니다. 예전 개발판이 자동 생성한 비밀번호를 이 화면이 복구하거나 변경하지는 않습니다.

관련 검사와 실제 실행의 구분은 [최초 계정 검증 기록](initial-account-verification-2026-10-17.json)을 확인하세요. 실제 새 배포판의 설치→서버 시작→브라우저 로그인 검사는 별도이며, 타입·단위·합성 브라우저·Compose 설정 파서 검사를 그 결과로 대신하지 않습니다.
